# Domain Naming Decision Log

## Decision Rules
- Every new canonical term must be logged before broad reuse.
- Decisions must include rationale and propagation scope.
- Conflicting synonyms must be resolved here first.
- Decision IDs must be unique and immutable; revisions must update the existing row or reference supersession, never duplicate an ID.

## Decision Evidence Appendix (Agent-Optimized)

### DDD-096
- Decision detail: `ArtifactCoherenceDiagnostic` is the deterministic pre-generation assessment envelope over `messageLevel`, `proofLevel`, and `ctaLevel`.
- Decision detail: `ArtifactCoherenceScore` is a derived `0..100` value and never user-entered.
- Decision detail: `ArtifactCoherenceMismatch` represents one typed misalignment finding; `CTAProgressionTarget` models expected CTA progression from message baseline; `CoherenceSeverityLevel` classifies mismatch gravity in machine-readable form.
- Ownership: Generation defines scoring semantics and severity rules; Frontend/UI computes and renders readiness-facing projections.
- Evidence rationale: deterministic three-dimension coherence model aligns with current map-driven readiness governance (`DDD-080`).

### DDD-097
- Decision detail: `ReadinessQualityGate` evaluates generation start eligibility from diagnostic quality outcomes, not only payload presence.
- Decision detail: `ReadinessQualityThresholdByTool` is an explicit per-tool policy map for score/severity acceptance.
- Governance constraint: threshold policy must be map-driven; fixed-count hardcoding and copy-text-dependent branching are forbidden.
- Ownership: Generation is authoritative for gate semantics; Frontend/UI projects gate status and reason codes in `ReadinessSnapshot`.
- Evidence rationale: extends existing readiness policy model (`ReadinessRequiredExtractionFieldKeysByTool`, DDD-080) with quality gating.

### DDD-098
- Decision detail: `ArtifactOutcomeStatus` canonical values are `not-tested`, `worked`, `failed`, `inconclusive`.
- Decision detail: `ArtifactOutcomeRecord` persists one outcome annotation over an Artifact with normalized tags and audit timestamps.
- Decision detail: `ArtifactComparisonSet` provides bounded comparison over two or three outcomes; `ArtifactLearningFeedbackLoop` feeds outcome evidence into readiness/advisory and regenerate strategy selection.
- Scope: domain-wide across all Artifact-producing workflows, including but not limited to `meta-ads`.
- Ownership: Generation owns persistence semantics and orchestration advisory consumption; Frontend/UI owns entry, visualization, and comparison projections.

### DDD-099
- Decision detail: `CoherenceDiagnosticReasonCode` and `ReadinessQualityReasonCode` are canonical typed code sets for diagnostic findings and quality-gate outcomes.
- Decision detail: `CoherenceReasonCodePolicyByTool` and `ReadinessQualityReasonCodePolicyByTool` are canonical per-tool map-driven policy sources.
- Contract-first rule: code sets and policy maps must be defined and approved in contracts/docs before FE/BE runtime control-flow branches are introduced or modified.
- Runtime constraint: runtime logic must consume existing map policies and reason-code sets; ad-hoc literals first/documentation later is forbidden.
- Evidence rationale: extends map-driven governance pattern already established by DDD-080, DDD-090, and DDD-097.

### DDD-129
- Decision detail: **Superseded by DDD-131 revision 2026-06-20.** SerpApi-only crawling for GEOMETRIC `serp-crawling` step (`WorkflowStepType = 'crawling'`, DDD-116).
- Decision detail: The SERP API is configured through the existing `ApiService` system (DDD-102) — no dedicated adapter is introduced.
- Decision detail: `ApiService` binding uses `workflowStepType = 'crawling'` (not `'acquisition'`) — the SERP API is a data acquisition **channel** for the crawling step, not a change to the step type.
- Decision detail: Domain translation layer maps SERP API response fields to canonical crawling concepts: `organic_results[]` → `SerpSource`, `answer_box.snippet` → `SerpAIOverviewSnippet`, `related_questions[]` → `PAAQuery`.
- Rationale: Google blocks direct browser automation scraping (sourceCount: 0 in production logs). SerpApi provides reliable structured data without requiring browser automation infrastructure. Removing Puppeteer reduces Docker image size, build time, and maintenance surface.
- Scope: Crawling & Extraction Context, Generation Context (via `invokeCrawling` actor).
- Related: DDD-114 (Crawling & Extraction Context), DDD-116 (WorkflowStepType = 'crawling'), DDD-102 (ApiService).

## Asset Domain — Project Workspace Evolution (DDD-188 through DDD-207)

The following block of 20 decisions introduces the **Asset** domain model, enabling the evolution from monofunctional tools producing session-scoped Artifacts to a networked project workspace where Assets are first-class, cross-tool reusable project property. See `docs/02-design/proposal-tool-output-personalization.md` §2 and `docs/02-design/domain-bounded-context-map.md` for architectural context.

### Base Asset Model (DDD-188 through DDD-195)

| DDD-188 | 2026-07-16 | Asset | `Asset` is the canonical **Entity** (Generation context) representing a persistent project resource that can be used as input across multiple Tools. ### Versioning and Derivation (DDD-196 through DDD-198)

| DDD-196 | 2026-07-16 | AssetVersion | `AssetVersion` is the canonical **Value Object** (Generation context) representing an incremental version of an Asset. Each time an Asset is updated (via regeneration of the source Artifact and re-promotion, or via manual edit), a new `AssetVersion` is created. Shape: `{ versionNumber: number, assetId: string, content: string, sourceArtifactId?: string, createdAt: string }`. The current version is always the highest `versionNumber`. Past versions are retained immutably — they are never deleted, enabling rollback and audit. Consumer `AssetReference` always resolves to the current version at dispatch time (snapshot semantics — once a generation starts, it uses the version current at that moment; later updates do not affect in-flight generations). Version history is a property of the Asset, not a separate entity. | `Artifact` is immutable by design (generation output record), but `Asset` must evolve (improve an angle, update a persona). Without versioning, updating an Asset would either (a) overwrite content silently, breaking audit, or (b) require delete+recreate, breaking references. `AssetVersion` enables iterative improvement while preserving: traceability (which version was used for which downstream generation?), rollback (revert to v1 if v2 is worse), and reference stability (in-flight generations snapshotted). | Generation |
| DDD-197 | 2026-07-16 | AssetDerivationChain | `AssetDerivationChain` is the canonical **Entity** (Generation context) tracking the genealogical relationship between Assets: Asset A was used as input to produce Asset B. Core fields: `upstreamAssetId: string`, `upstreamVersion: number` (version of A at time of B's creation), `downstreamAssetId: string`, `toolKey: ToolKey` (the Tool that performed the derivation), `sessionId: string` (the GenerationSession where B was produced), `createdAt: string`. When an upstream Asset is versioned, all downstream Assets in the chain are evaluated for staleness per `AssetStalenessPolicy` (DDD-198). The chain is populated automatically when a `GenerationRequest` carries `AssetReference`s and the generation completes successfully — the resulting Artifact (if promoted) inherits the derivation links. | Without derivation tracking, updating a source Asset (e.g., regenerating an angle) leaves downstream Assets (e.g., meta-ads copies based on the old angle) silently stale. The user has no way to know which Assets are affected. `AssetDerivationChain` makes dependencies explicit, enabling: (1) impact analysis ("which Assets will be affected if I update this angle?"), (2) cascade suggestions ("the source angle was updated — regenerate these 3 downstream Assets?"), and (3) quality degradation detection (stale downstream assets). The DAG structure supports complex multi-step derivation (angle → meta-ads → A/B test report). | Generation |
| DDD-198 | 2026-07-16 | AssetStalenessPolicy | `AssetStalenessPolicy` is the canonical **Policy** (Generation context) governing how downstream Assets react to upstream version changes. Rules: (1) When an Asset is versioned (new `AssetVersion` created), all directly downstream Assets in the `AssetDerivationChain` are marked with a `staleUpstream` flag — they remain `active` and functional but display a warning indicator. (2) When an Asset with `staleUpstream` is used as input, the backend logs a warning and the FE shows an advisory: "This asset was generated from an older version of [upstream Asset label]. Output may be suboptimal." (3) The user can dismiss the staleness warning for a specific generation (acknowledge-and-proceed) or regenerate the downstream Asset using the new upstream version. (4) Staleness is **not** automatically resolved — only explicit user action (regenerate or dismiss) clears the flag. (5) Archiving or deleting an upstream Asset marks all downstream Assets with `staleUpstream` permanently (the source is gone — no regeneration possible, only dismissal). | Automatic invalidation of downstream Assets on upstream change would be destructive (in-progress work lost) and confusing (Assets disappear without user action). Complete silence about staleness would degrade output quality over time. The staleness-warning approach balances safety with autonomy: the system surfaces the dependency change without forcing action, leaving the user in control of when to regenerate. | Generation |
